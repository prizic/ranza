# Pilot export formats

Operator Owners request their own asynchronous archive from `/{locale}/staff/exports`, linked from the staff home. Only the original requester can see or download their archive; authorization is rechecked against current Owner status, Operator, ready state and expiry before a private Storage URL is signed. The URL is a bearer link valid for 60 seconds. Protect downloaded personal data and never share signed URLs. Worker deployment and archive-generation verification remain separate release gates.

Meal CSV uses UTF-8 and CRLF with eight fixed columns: `student_access_id,student_name,response_status,selected_meals,corrected,record_type,total,value`. Named entries have `record_type=student`; their final two cells are empty. Summary entries have `record_type=total`, empty Student fields, a stable metric key and integer value. Metrics are eligible_students, responded, zero_meal, unconfirmed, breakfast, lunch, dinner and corrections, in that order. Effective kitchen counts are calculated from the same exported final/corrected rows, not a second racing query. An empty eligible roster still exports zero totals. Consumers of the former five-column pilot format must accept the three appended columns and filter record_type as appropriate.

Support job retries reuse successful results. Failed results can be retried after 60 seconds, with at most three attempts per source job. Every actual attempt requires a current support context and reason and emits an audit record; requests during cooldown or after exhaustion return the cached result without re-executing the finalizer.
