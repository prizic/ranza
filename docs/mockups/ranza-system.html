One database, isolated by policy

All three applications share one Supabase PostgreSQL with row-level security. Tenant boundaries are database facts, not UI conditionals: every customer-owned row carries operator_id, every Branch-scoped row carries branch_id too, and denial is proven by test for the Student next door, the unassigned Branch, the other Operator, the stale transfer and the manipulated export scope.

Workspace packages

  • domain — vocabulary, validation, state transitions, capability names. No Next.js, no Supabase.
  • database — generated types, typed query boundaries, RPC clients, repositories.
  • auth — staff session helpers, Student Credential Gateway contracts, role resolution.
  • ui — design tokens and presentational primitives. No tenant data access.
  • i18n — Turkish, English, Arabic catalogs, locale negotiation, RTL rules.
  • config — runtime environment validation and feature-catalog schemas.
  • observability — structured logging, correlation IDs, redaction rules.
  • supabase — ordered migrations, database functions, RLS tests.

Pilot modules

Nightly Attendance

One declaration per Student per Branch-local date: Staying, Away, or Unconfirmed. Silence is never read as either answer. At the Branch cutoff an immutable, idempotent Snapshot is written; later changes are corrections with a recorded reason.

Away is an operational declaration, not an approved leave request.

Next-day Meals

A Branch publishes breakfast, lunch and dinner opportunities for a service date under one immutable UTC deadline. Students opt in explicitly, including an explicit zero-meal response, which stays distinguishable from no response at all.

No free-form menu, no quantities, no pricing.

Announcements

Draft, publish, revise, archive. Targeted to the whole Operator or named Branches, with optional human translations and a labelled fallback language. A material edit creates a new revision and resets acknowledgment.

Opening or receiving is never acknowledgment.

Student Balance

Append-only ledger of Charges, External Payment Records, Credits, Adjustments and Reversals in fixed-precision numerics. Mistakes are corrected by linked reversal, never by edit or delete.

Ranza records money information. It never collects or transfers money.

Wi-Fi Access Information

Per-Branch network details, encrypted at the application boundary. Protected mode serves active Students and assigned staff; Public/QR mode serves a revocable, expiring anonymous token. Audit records that Wi-Fi changed, never the secret.

Rotating the link does not require changing the password.

Entitlements and configuration

Prizic owns the Feature Catalog: which capabilities exist, which modes are supported, what ranges are allowed. Operators configure inside those boundaries. One product, no customer forks.

Three ways in, one identity model

Each actor class authenticates differently because each has a different practical constraint — a Student may have no email at all — but all three end up as an ordinary Supabase session whose authority comes from database membership records, never from user-editable metadata.

Student

Activation Code, then PIN

  1. Staff create the roster record first.
  2. Staff issue a non-secret Student Access ID and a high-entropy, expiring, one-time Activation Code, shown once.
  3. The Student exchanges the code for a PIN of their choosing.
  4. Later sign-ins use Access ID + PIN through a rate-limited server gateway.

The PIN is never stored. A server-only gateway derives an Auth password with a versioned keyed derivation; logs, audit records and tables never see either value. A forgotten PIN is an audited staff-assisted reset, never a second identity.

Dormitory team

Email magic link

  1. The Operator Owner registers the work email.
  2. Staff request a sign-in link from the dashboard.
  3. The callback exchanges the code for a session.
  4. Role and Branch assignments are resolved from operator_memberships and branch_assignments.

Losing a membership row removes access immediately, with no session to revoke by hand.

Prizic

Invitation, password, MFA

  1. An existing Platform Admin issues an invitation; there is no self-service signup.
  2. The invitee accepts, which exchanges the invite token hash for a session.
  3. They set a password of at least 12 characters.
  4. Every internal page requires assurance level aal2 — TOTP — before it renders.

Platform identity lives in a non-exposed schema, separate from any Operator membership.

Data model

Forty-four relations. Every exposed table has row-level security enabled and default-deny grants; credential mappings and cryptographic material live in a non-exposed private schema.
