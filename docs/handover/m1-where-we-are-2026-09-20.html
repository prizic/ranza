02

What Ranza is, in a page

Ranza is a multi-property accommodation platform — hotels, hostels and student residences run from one product, where a student residence is a configuration of a Property, not a separate product (ADR 0004). One Organization owns several Properties; a Property is divided into Accommodation Units — a room, or a bed under a room. A Guest (a Resident is a kind of Guest) gets a Reservation for some nights, which becomes a Stay at check-in, which opens a Folio that money is posted to.

The whole product is delivered as vertical slices: a module that owns its tables, hand-written row-level security policies proved by tests, a read through one server funnel, a screen, and the entitlement gate that reveals it. Blueprint section 13 forbids building tables ahead of the workflow that needs them, which is why most of the rail is deliberately unbuilt.

Vocabulary that is enforced

The repository used to be a dormitory pilot. That vocabulary is superseded and its reappearance is treated as a bug, in code, database names, issues and prompts.

Never Use
Operator, Dormitory Operator, tenant Organization
Branch Property
Student Resident (a Student is a Resident type)

Three tiers, one direction

Tier Rule Examples
packages/platform/ Host-agnostic. May not even mention Property, Guest, Resident, Stay, Reservation, Unit or Folio — a script scans the source text. audit, outbox
packages/ranza/ The domain. Hospitality language is fine. core, accommodation, reservations, guests, folios, staff
packages/adapters/ Translates between the two. Nothing depends on it.

Modules expose index.ts only, receive their dependencies through a deps object, and never read process.env. In the workspace app, nothing outside src/server/ may import a module or the database — server/viewer.ts is the one path to tenant data (ADR 0007). All of this is enforced by pnpm check with fixtures proving each rule fires.

The security posture, in three lines

  • Row-level security is the authorization boundary. The runtime role ranza_app owns nothing and cannot bypass it.
  • A write is bounded by a policy carrying all five gates of blueprint 3.5 — subscription, entitlement, Property capability, the Staff Member's permission, and the row — not by an application check (ADR 0012, amended by ADR 0026). A policy bounds rows; a column-level grant bounds what can be changed.
  • A passing security test proves nothing until you have watched it fail. Break the boundary, confirm red, restore.

RANZ-27

Rooms & beds

to do high due Sep 23 databasefrontendmigration blocks 25 · 28 · 33

"Sold by the bed" is the sprint goal's own phrase, and it is what ADR 0004 exists for: a student residence is a Property whose Units are beds. The decision and the database are done; the screen and the first write path are not.

Exists on main

  • ADR 0025 and migration …002100: a bed is a Unit with a parent; a Unit is sellable when it has no children (derived, never a flag); building and floor are columns.
  • Triggers: a Stay or Reservation may not name a Unit with children; a Unit somebody is in may not be divided.
  • A bed may stand alone — a parentless bed is a dormitory, and requiring a room would have refused existing rows.
  • listBookableUnits and createReservation both take leaves only.
  • tests/database/unit_hierarchy.test.sql, 22 assertions, each watched go red.

What is new

  • The screen: bed map, bed list, occupancy counts, bulk add, blocking a bed with a reason.
  • The first write policy on accommodation_units — five conditions from the start, since nothing writes a Unit through the application today.
  • A permission in public.staff_permissions, something like accommodation.configure, in the same migration. There is no accommodation permission yet.
  • Where it lives in the rail: the mockup has a Places group (Rooms, Housekeeping, Maintenance); blueprint 4.6 puts Unit settings under Configuration. Decide, and say why in the PR.

Watch out

  • Unique-within-parent is two partial indexes because null ≠ null in a unique index; keep the assertion that the room case still fails.
  • A permission not in the catalogue is refused by a trigger — a typo fails loudly, which is the point.
  • "Block a bed" is a status write. Do not invent a fourth status here that Housekeeping then has to reconcile — read RANZ-28 before choosing the value.
  • Fix the three stale roadmap rows ("Units are flat") in the same commit.

Read: ADR 0025 · ADR 0012 and 0026 · packages/ranza/staff/README.md (which rule lives where) · migration …002300 (amended policies side by side). Mockup: #rooms.

09

How a screen gets built here

The same five steps every time, from the handover doc. Arrivals and departures are the worked example; reservations is the most recent one that added a table as well as a screen.

  1. The module

    A package under packages/ranza/ owning its tables, with the migration carrying schema, policies and grants together. Flat until it has a rule SQL cannot hold.

  2. The policies, and the tests that prove them

    A pgTAP suite in tests/database/. Then break each boundary and confirm it goes red. Three suites in this repository have been green while verifying nothing.

  3. The read, through the funnel

    Add it to src/server/viewer.ts. Nothing outside src/server/ imports a module or the database; a fixture proves the rule fires.

  4. The screen

    A folder under src/features/<domain>/ with the table, columns, detail panel and row actions. Presentational; data arrives as props. Tailwind and shadcn only — no CSS files, logical directional utilities so Arabic mirrors for free.

  5. The gate

    built: true in src/lib/screens.ts and a capability row in scripts/db-seed-dev.mjs. Copy in Turkish, English and Arabic through the typed catalogue — a missing string is a type error.

Before any of it: the feature-design skill in .claude/skills/feature-design/ writes the use cases, states and edge-case rows into docs/features/<feature>/. A feature is designed before it is coded; the audit-log folder is the freshest example of the shape.
