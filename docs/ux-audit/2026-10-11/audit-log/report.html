UX audit: Audit log

Route /en/audit-log (also ?record=, filters) · persona: the owner investigating "who changed this rate / who cancelled that booking / why does this balance differ?" under pressure · roles: Owner (primary), Manager, Front Desk, Finance · staging, 2026-10-11 · audit-only mode, nothing submitted or changed. Every claim is labelled verified (I saw it), inferred (read in code or docs) or unknown.

1. Verdict

  • Can the owner use it unaided? Mostly yes for "who touched this room or guest": search by room number, guest or colleague, the action and day filters, and a record that opens by link all worked first time (verified, 15 records).
  • Biggest risk: the page answers "what happened" but not "what did it change" or "where is the thing it changed". The list never shows before/after values, and the event's subject (reservation, stay, room) is not a link, so the owner has to open each record and then go hunt for the booking by hand. Folio is the only subject that links, and nothing links back from a Folio to its history.
  • Second risk: search does not match the action words ("rate" finds nothing), and a search that matches more than 200 Guests or rooms is capped without saying so (inferred; staging is too small to see it).
  • Not provable on this data: staging holds 15 records in total and none of them is a cancellation, a Folio line, a rate change or a closed day, so how those rows read is judged from code and tests (inferred), not seen.
  • Good base: plain-language action names in three languages, actors as addresses with "You" for the viewer, Property-local times, correct refusal for a role without the permission, working back button.

4. Top changes, ranked by time saved x frequency

  1. I can see what a change did without opening the record: before and after on the list row (AUDIT-09, with AUDIT-01).
  2. I can go from an event to the booking, stay or room it is about, and from a Folio or reservation to its history (AUDIT-02, AUDIT-03).
  3. I can type the words I think in ("rate", "cancelled") and find the events, or am told to use the Action filter (AUDIT-04).
  4. I can read the first line of every reason in the list (AUDIT-05).
  5. I am told when a search was too broad to be complete (AUDIT-11).
  6. I can see who did it on my phone (AUDIT-06).
  7. Every action reads in plain words in the detail, never a field name (AUDIT-01).
  8. The same thing has the same name everywhere (AUDIT-08).
  9. I can export what I am looking at or am pointed to where (AUDIT-12).

5. Inconsistencies with sibling screens

  • verified Reservation vs Booking, Accommodation unit vs Room/Unit, Business day vs Close the day (AUDIT-08).
  • verified The record screen shows a plain "Role changed" From/To but a raw-key "Departure changed": two writers, two levels of finish (AUDIT-01).
  • inferred Today's activity card links into specific records (code, activity-card.tsx), but the log's own rows do not link outward; Today does it better.
  • verified Back arrow works as ADR 0035 asks: the list goes to Today, a record goes to the list with the filters kept (record page Back link equals the list URL).
  • verified The Front Desk rail has no Data export, Integrations or Audit log, so a role without the permission never sees a dead entry, matching the rule on other screens.

6. Not built / needs backend work

  • Denied and failed attempts are not recorded or visible. There is no action in the catalogue for a refusal or a failure (56 known actions, none of them a denial), and each record commits in the same transaction as the action it describes, so a refused action leaves no row by design (use-case.mmd, edge-cases.csv AL-S1-15 and the written note "the record and the action it describes commit together"). Failed and successful sign-ins are out of scope (AL-DEF-05, blueprint 7.6). An owner asking "who tried to cancel that?" has no answer here. inferred
  • Today's note that refused actions may have left rows: from event type alone I cannot tell. Since 30 Sep the log gained exactly one row, a "Reservation taken" at a Property on 11 Oct, written by the Manager account; a taken reservation means the action succeeded, not that it was refused. Nothing in the list reads as a refusal. verified (list), conclusion about cause unknown.
  • Export of the audit log exists as a dataset on the Data export screen, proposed in ADR 0043, and is out of scope for this screen (AL-DEF-04). The missing part is only the pointer (AUDIT-12).
  • Invitation accepted is not recorded (AL-DEF-06, deferred).
  • No live updates: a record written while the page is open is not there until reload, by design (AL-S1-13).
  • No sort, no actor filter: newest first only; person is found through free-text search. Not in the feature design; I did not find a deferred row for it. inferred

7. What already works well and must not regress

  • Plain-language action names with a correction badge (warning tone + icon + word) for reversals (05; badge from code).
  • Actor shown as a person's address, "You" for the viewer (13), never a bare id. A display name is not used; addresses are the identity here (AL-S1-10).
  • Filters, search and paging are server-side URLs: every filtered view is shareable, and "1 record" / "15 records" pluralise correctly (09). Page size is 50 with a newest/older link pair (code; staging has only one page).
  • Period picker with presets and a clear range summary (08).
  • Record opens by id and keeps working; a wrong id gives one calm message (10).
  • The no-permission page tells the person why and who can fix it, without saying the Subscription lacks a module (14).
  • Arabic mirrors correctly, including the filter bar and table order (12).
  • The audit log stayed clean during this audit: nothing was submitted, and the count was 15 before and after my reads (sign-in is not logged here).

Notes and limits

  • Keyboard use: I checked the structure, not real key presses. The filter form is a native GET form whose tab stops are Action, Property, From, To, Search, Apply, in that order, all real buttons or inputs, and each row has exactly one link (15 rows, 15 links), so a record is reachable by Tab and Enter (verified in the DOM). Focus rings and the Escape behaviour of the pickers were not driven by keys.
  • Not testable on this data: the "Older records" link and the "Newest" link (staging has one page of 15), a second user opening a shared record link, and the Property filter with more than one Property. These stay inferred from code as stated above.
  • Sign-in was done once per role (Owner, Manager, Front Desk, Finance). The first Owner attempt landed back on the sign-in page and I retried once; no rate-limit message appeared.
  • The Manager account saw the same 15 rows as the Owner, including "Whole Organization" records. This is consistent with AL-S1-19 (a writer reads back its own records), because every one of those rows was written by that account; I could not verify the narrowing for an assigned-Property reader on this data.
