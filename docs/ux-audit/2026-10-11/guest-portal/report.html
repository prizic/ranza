UX audit: Guest portal (sign-in and My stay)

Audited 2026-10-11 against hosted staging, https://ranza-portal.46-225-168-54.nip.io, mode AUDIT ONLY. Persona: a hotel guest on their own phone, possibly Turkish or Arabic speaking, who gives up fast. Primary width 375 px.

1. Verdict

I did not see the signed-in experience. No guest or Resident test account exists in CLAUDE.local.md, docs/ or docs/runbooks/, and the staff accounts are not valid on this host. I did not invent, create or reset one. Everything about /stay below is inferred from apps/guest-portal, ADR 0009, the edge-case CSVs and one older evidence screenshot.

1. Could this guest use it unaided? The sign-in page, yes: it is clean, fits 375 px with no horizontal scroll, uses 16 px inputs and mirrors correctly in Arabic. What follows sign-in answers one question in five: dates and room. Not the bill, not checkout time, not how to ask for anything.

2. Biggest risk: a locked-out guest has no way forward. There is no forgot-password page (404, verified), no "how do I get access" line, no contact. In addition, nothing in the application code I searched ever links a hotel stay to a portal account, so most hotel guests would reach the empty state even with a working password.

3. A departed or cancelled guest sees "You have no stay to show", the same screen as someone who was never booked. That is deliberate (ADR 0009) but it reads as a lost booking.

4. Top changes, by time saved times frequency

  1. When I cannot sign in, I am told what to do next (reset, or who to ask). GP-01.
  2. After I check out, I see that my stay is over, not that it was never set up. GP-02, copy first.
  3. I open the link in my language and it stays that way. GP-03.
  4. A wrong link lands me on a page that lets me get back to my stay. GP-04.
  5. When something breaks, I get a retry button, not a framework page. GP-04.
  6. The sign-in page only promises what exists. GP-05.
  7. The stay card reads in a guest's words. GP-06, GP-07.
  8. After a failed sign-in my keyboard cursor is where I need it. GP-08, GP-09, GP-10.

5. Inconsistencies

  • Staff Workspace vs Portal on stay state (inferred): staff screens can see departed and cancelled stays; the Portal hides them. The Portal's stayStatus catalogue still has four labels, two unreachable.
  • Back button (ADR 0035): the Portal has one destination, so no inner page exists to carry one. Fine today; becomes a requirement with the first detail view.
  • Vocabulary: the portal uses "Unit" and "Resident" for hotel guests, where the Workspace says Room and Guest.
  • Language: the staff Workspace and the Portal both keep language in the URL only.
  • Sign-in: the Portal reuses the Workspace's sign-in layout component. I did not check whether the Workspace offers a password reset, so I cannot say whether the Portal is behind or level with it (unknown).

6. Not built / needs backend work (not UX defects)

  • Guest request creation from the Portal: not built. docs/roadmap.md row "Guest and Resident services": "Missing: Guest Portal submission side". No route or form exists in apps/guest-portal/src; /en/requests is 404. Staff-side requests exist (GX-S1-*). verified (404) and inferred (code).
  • Bill or balance in the Portal: deferred, FO-DEF-11.
  • Reporting a maintenance problem from the Portal: deferred, MT-DEF-02.
  • Checkout time, check-in time, Wi-Fi, property contact, directions: not in OwnStay, so there is nothing to show. I found no deferred row for them.
  • Guest account provisioning: I found no code in packages/ranza/stays or packages/ranza/reservations that writes stays.user_id. The column is documented as nullable and "most Stays are created by Staff for someone who has never signed in" (OA-S4-06). I found no invite, link or sign-up flow for guests. inferred: I could not rule out a path I did not search, such as a seed script. Email and password sign-up is enabled in the auth module and the Portal has no sign-up screen; I did not touch that API.
  • Password reset and any email flow: none found.
  • Stay history, announcements, meal choices: listed in blueprint 4.3, unbuilt (apps/guest-portal/README.md).
  • Portal client error reporter: absent, per comments in sign-in-form.tsx.
  • Organization default language for a guest with no preference: deferred, CF-DEF-01.

7. What works well and must not regress

  • 375 px sign-in: no horizontal scroll, 52 px fields at 16 px so iOS does not zoom, full-width 52 px submit. verified
  • Arabic mirrors from the first render (dir="rtl", flag and chevron swap sides, labels right-aligned). Turkish and Arabic copy exist for every string. verified
  • Failure copy is honest: wrong credential, rate limit (429) and "not working" are told apart in code, and a 403 never says the password is wrong. Only the wrong-credential case was exercised. The message does not reveal whether the email exists. verified for mismatch; inferred for the rest.
  • Failed attempt keeps the typed email and password and marks both fields invalid with an announced error. verified
  • Empty submit is stopped by the browser before any request is sent (confirmed in code, no noValidate, and in the network list). verified
  • Muted subtitle contrast 4.56:1, submit button 8.77:1. verified
  • Signed-out /en/stay and /ar/stay redirect to sign-in in the same language, without a loop. verified
  • Stay page design intent (inferred from code): room name large at arm's length, dates in UTC so a calendar date never shifts a day, Arabic plural forms for capacity, one empty state that leaks nothing about commercial gates.

Mode compliance: one failed sign-in with a made-up address (401), one empty submit blocked by the browser. No account created, no reset or magic link requested, no other form submitted, no files edited outside this folder. The one unrequested copy in this folder (09) is a read-only copy of an existing evidence image from another worktree.
