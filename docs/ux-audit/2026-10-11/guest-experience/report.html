0. Data state, and what that does to this audit

Verified: the Property has zero guest service requests (all four counters read 0 for Front Desk, Housekeeping and Manager). I am not allowed to create one, so I never saw a populated table, a row action, a resolve/cancel dialog, or the 50-request case. Everything about rows, ageing, sorting, row actions and what a closed request looks like is inferred from requests-table.tsx, request-actions.tsx, server/guest-services.ts, the module packages/ranza/guest-services and migration 20260916009900_guest_service_requests. Where a finding is inferred I say so in the table. These are code-reading findings and I could not reproduce any of them in the browser.

1. Verdict

  • Could the front desk agent use it unaided? To log a request, yes (a short form, three required decisions, clear fields). To run a queue, no: there is no way to give a request an owner or department, no age, and no urgent-first order. Those are the three things the persona said they need.
  • Biggest risk: actions fail silently. Every status change discards the server's answer (code), so a refused change (permission, a database rule) looks like nothing happened, or like it worked because the dialog closes. Reopening a cancelled request is wrong against the database rule, so it can never succeed (inferred).
  • Loop with the guest is not closed: the Guest Portal cannot submit or see requests (README and roadmap say so), and resolving a request tells the guest nothing. The front desk must phone or walk to the room by themselves.
  • Sibling screens are ahead: Maintenance has assignee and priority filters, a read-only notice for people who cannot manage, and equipment context. Guest Experience has none of these, and its categories "Housekeeping" and "Maintenance" do not create or link to anything on those screens.
  • Layout is clean, English/Turkish/Arabic all render and Arabic mirrors correctly; only the 375 px tab strip overflows.

5. Inconsistencies with sibling screens

  • Maintenance: has assignee and priority filters, an Out-of-order concept, a read-only notice for non-managers, and an empty state with an action button. Guest Experience has an empty state with no action, no filters beyond status tabs, and no read-only treatment. verified (empty states, screenshot 05) / inferred (filters, notice).
  • Housekeeping: paginated table ("Page 1 of 1", per page 10); Guest Experience is not paginated. verified for Housekeeping, inferred for Guest Experience.
  • Overlapping categories: a Guest Experience request of category "Housekeeping" or "Maintenance" is a separate record that never appears on those screens (no code links them). A leaking tap reported here is invisible to Maintenance unless someone re-types it. inferred (grep found no reference between the modules).
  • Status words: Guest Experience uses New / In Progress / Resolved / Cancelled; its button reads "Start Working" while the status reads "In Progress". Maintenance and Housekeeping use their own sets (Dirty/Clean/Inspected; waiting for parts, overdue). Not checked in depth.
  • Turkish: "Konuk" in the title and "Misafir" in the body of the same page. verified
  • Back button: present (top bar arrow, goes to Today), as ADR 0035 asks. There are no detail views to check; all work happens in rows and dialogs. verified

6. Not built / needs backend work

  • Guest Portal submission and viewing of requests. The Portal README says: "Blueprint 4.3 lists more (service requests ...) and none of them are built"; docs/roadmap.md says "Missing: Guest Portal submission side". The portal has only the stay page. So there is no arrival path from the Portal today, and I cannot say how it will look when it lands. inferred from README, roadmap and file list.
  • Telling the guest when a request is closed (message, push, Portal status). No notification code in the module. Real-time guest chat and post-stay survey are marked "Not this slice" in use-case.mmd.
  • Departments/teams as assignees. The data model only has an assigned user (assignedToUserId); "assign to housekeeping" as a team is not modelled. A person picker is the part that is already half-built (GX-01).
  • Ageing/SLA targets per priority: no field or configuration exists. Showing relative age (GX-04) needs no backend; "overdue after N minutes" needs a setting.
  • Edit a request (title, priority, category, room): the module supports it (updateRequest accepts those fields) but there is no UI, and no detail view. Not listed as deferred in edge-cases.csv.
  • Edge-case rows are all slice 1 (GX-S1-01..18); slice 2 "stay link" has no rows in edge-cases.csv, so GX-07 is not covered by an approved row.
