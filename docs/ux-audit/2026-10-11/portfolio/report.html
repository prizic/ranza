UX audit: Portfolio (All Properties)

Route /en/portfolio · Staging ranza.46-225-168-54.nip.io (code identical to main 4b15c30 per the brief) · 2026-10-11 · Persona: a multi-hotel owner comparing Properties each morning · Mode: audit only, nothing was submitted or changed.

Data state, stated first because it limits everything below. On staging the Organization “Prizic Demo” has exactly one Property reachable by every account I could test. I signed in as Owner, Manager and Front Desk (verified); all three reach only “Demo Otel İstanbul”. The Owner’s Property switcher lists that one Property and no other (verified, menu opened and closed without selecting). I was told not to create a second Property, so I never saw the populated comparison page. Everything about 2 vs 12 Properties, ranking, currencies and click-through is judged from code and the feature docs and is labelled inferred. Finance and Housekeeping accounts were not tested (not asked).

1. Verdict

  1. Could this persona use it unaided? Not on staging: the rail correctly hides the page from a one-Property viewer, and a typed URL gives a clear “Nothing to compare yet” with a way out. That part works (verified, three roles, three languages, phone width).
  2. The populated page, from code (inferred): it is accurate and careful (null is never zero, occupancy is summed counts, money is never added across currencies, each card keeps its own business date), but it is a read-only grid of cards in alphabetical order.
  3. Biggest risk to the stated job (“click into the one that is behind”): nothing on the page says which Property is behind. No sort, no ranking, no highlight, and the occupancy share is a small caption under a raw count, so a 40-room and a 10-room Property cannot be compared at a glance (PORTFOLIO-01).
  4. Second risk: the money summary tile has no “counted at x of y” note, so when some Properties hide money the total is understated and reads as fact; the code promises exactly that guard for the other two tiles (PORTFOLIO-02).
  5. One verified defect: a stale or wrong ?property= shows “This module is not in your Subscription”, which is the wrong reason (PORTFOLIO-03).

PORTFOLIO-02 causes errors /portfolio, any viewer where money is hidden at some Properties but not others The Money owed summary tile is built without a coverage prop (summary-stats.tsx, second SummaryCard). balancesOf() in server/portfolio.ts skips null balances, so a Property with billing off drops out of the sum silently. 4. Top changes

  1. I can see which Property is behind at a glance: share of occupancy as the headline figure plus a sort (PORTFOLIO-01).
  2. I can trust the money total: it says when it was counted at fewer Properties than are listed (PORTFOLIO-02).
  3. I can go from a number that looks wrong straight to the list behind it at that Property (PORTFOLIO-04).
  4. An old bookmark tells me the real reason and takes me to my Property (PORTFOLIO-03).
  5. With twelve Properties I can scan them in one screen and see the date the figures belong to (PORTFOLIO-06, -05).

5. Inconsistencies

  • Same measure, two names: tile “Occupancy across Properties” vs card “Units in use” (PORTFOLIO-07). inferred
  • Guard applied twice, missed once: occupancy and maintenance tiles print coverage when partial; the money tile does not (PORTFOLIO-02). inferred
  • Not-available state reused with wrong reason: the page uses the “module not in your Subscription” copy (notEntitledTitle, a shared key, inferred to be used by sibling module screens too), but here it also fires for an unreached Property id (PORTFOLIO-03). verified
  • Doc says Analytics shows 0 percent with no sellable units, the portfolio shows a dash: deliberate and recorded (PF-S1-16); a user who sees both screens will see different treatment. inferred

6. Not built / needs backend work

Not defects. Sources are in docs/features/portfolio/edge-cases.csv and docs/handover/operator-workspace-screens.md row portfolio.

  • Enterprise-plan gate: undecided owner question (PF-S2-02). Its absence is not reported as a defect.
  • Charged this month: deferred, needs a definition (PF-DEF-01).
  • Occupancy trend: deferred, no real series exists (PF-DEF-02).
  • Money total across currencies: deferred, needs a rate source (PF-DEF-03). The summary correctly shows one line per currency.
  • A closed (archived) Property’s history in the portfolio: deferred (PF-DEF-04).
  • Event sink for portfolio.viewed: console line only for now (PF-DEF-05).
  • Sorting, filtering, ordering by anything but name and deep links from figures: no edge-case row asks for them (the only ordering row is PF-S1-27, name then id). I treated them as UX gaps (PORTFOLIO-01, -04, -06), not as features the owner already deferred; the owner can reclassify.
  • Two Organizations: compared one at a time by choosing a Property in the other (PF-S2-14), by design.

7. What already works well and must not regress

  • A viewer who reaches one Property gets a plain explanation, the Property’s name and a working “Go to Today”, in English, Turkish and Arabic, at 375px, with no console errors (verified; figures 01 to 03, 05 to 07).
  • The rail offers the page only where it can show something (verified absent from all three roles’ navigation here; rule in lib/portfolio-offer.ts, inferred for the populated case).
  • Back button on the inner page, to Today with the same Property (verified).
  • Design rules in code that protect the owner from a wrong comparison (inferred, from derive.ts, property-card.tsx, server/portfolio.ts): a null figure is “Not available” or “Hidden”, never 0; occupancy is summed counts, not an average of percentages; no share when nothing is sellable; money is one line per currency and each card is in its own currency; each card carries its own business date; a Property without Analytics stays in the list as “withheld” and can still be opened; one SQL statement gives one consistent snapshot; a portfolio over 200 Properties is refused rather than truncated.
  • Loading skeleton makes no claim about counts; the error boundary offers “Try again” and logs the error (inferred).
