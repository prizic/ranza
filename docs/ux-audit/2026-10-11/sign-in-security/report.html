Sign-in and account security

UX audit, 2026-10-11. Hosted staging, main 4b15c30. Persona: a Front Desk receptionist starting a shift on a shared desk PC (sometimes a phone), and the Owner who should turn on two-factor. Mode: audit only, nothing persisted.
Surfaces: /{en,tr,ar}/sign-in, signed-out root and deep links, the account menu, /en/security (two-factor panel).
Labels: verified = I saw it in the running app; inferred = read in code or docs, not run; unknown = could not find out.

1. Verdict

The sign-in itself is good; the session around it is not finished. A receptionist can sign in unaided in about half a second of server time, on a phone too, in all three languages, with clear error copy (verified). The biggest risk is the shared desk PC: there is no sign-out control anywhere (verified on desktop and 375 px), sessions last about a week and extend on use (inferred, OA-NB-03), so the next person at the desk is the previous person, and every action is attributed to them. The Owner can find Security in two clicks from the avatar, but nothing points them to it, and the two-factor enrolment will be hard to complete on a desktop (setup key only, no QR) and risky to complete (backup codes are shown once with no way to save them, and no self-service recovery exists). A session that ends mid-task, or a deep link opened while signed out, drops you on a bare "Welcome back" with no explanation and no return to where you were (deep link verified; expiry inferred).

4. Top changes, ranked by time saved times frequency

  1. I can end my shift and the next person cannot act as me (SIGN-01).
  2. I sign in and land on the page I was trying to open, and when my session ended the screen says so (SIGN-02).
  3. Setting up two-factor on a computer takes a scan, not a typed key, and I can save my backup codes before the screen takes them away (SIGN-07, SIGN-06).
  4. When turning two-factor on fails, the screen tells me the truth and the button works again (SIGN-05).
  5. The app opens in the language I used last (SIGN-03).
  6. When a password is wrong or I am throttled, I am told what to do and how long to wait (SIGN-04).
  7. The Owner is told two-factor exists and is off (SIGN-08).
  8. I can see who is signed in at a glance, by name (SIGN-09).

5. Inconsistencies

  • Error handling: the sign-in form separates "did not match", "too many attempts", "challenge spent" and "not working" (with tests in sign-in-form.test.tsx); the Security panel, a few clicks away, collapses everything into "did not match" (SIGN-05). The sign-in form is the better one.
  • Show password: sign-in has the toggle, the Security password field does not (SIGN-11).
  • Who am I: the Today greeting uses the display name, the account menu uses the email (SIGN-09).
  • Tab titles: every page is titled "Ranza" even though page-titles.ts gives pages names for the bar (SIGN-10).
  • The sign-in page follows EduBoard rather than Leaders by owner decision; I did not treat that as an inconsistency.

6. Not built / needs backend work

  • Sign out: not built in either app. Docs row OA-NB-01, status open, "whether it is simply missing or waits on a decision has not been said". Listed in findings because it is the largest risk for the shared-desk persona, and cheap.
  • Forgotten password: no recovery or change-password flow; recovered by a database operation. OA-NB-02, not scheduled. (SIGN-04 asks only for a next-step sentence, not the flow.)
  • Lost authenticator and backup codes: no self-service or support-assisted reset. OA-DEF-01 (deferred), ADR 0010, and docs/roadmap.md "Decisions not yet applied".
  • Requiring two-factor for a role or Organization: roadmap says nothing can require it yet.
  • Session lifetime and idle timeout for a shared desk: not decided, OA-NB-03.
  • Viewing status or regenerating backup codes after enrolment: nothing in the docs or code; unknown whether planned.

7. What already works well and must not regress

  • Enter submits; sign-in answers in about half a second (verified).
  • Wrong credentials: one neutral message that does not say which half was wrong; email and typed password kept; focus stays in the password field; fields marked invalid; message in a live region (verified, 05).
  • Show/hide password with an accessible label that changes (verified).
  • Correct autocomplete tokens (username, current-password, one-time-code), so password managers and SMS or authenticator autofill work (verified in the DOM).
  • 375 px: fits above the fold, no horizontal scroll, 16 px inputs (verified, 03, 09).
  • Arabic sign-in and Security mirror correctly with Arabic labels and no overflow (verified, 04, 11). Turkish sign-in verified (01); Turkish Security copy read in messages.ts only.
  • Security page has a back button to Today (ADR 0035, verified) and the Security link keeps the active Property.
  • The enrolment design (secret written unverified, account untouched until a code proves the app has it) means a mis-scanned key costs a retry, not the account (inferred from ADR 0010 and the module comment).
  • A challenge spent by five wrong codes goes back to the password with its own message, instead of leaving a dead form (inferred from code and tests).

Scope and limits of this audit

  • One wrong-password attempt on the Housekeeping address, and one correct Front Desk sign-in (needed to reach Security). Before the attempt I read the auth module: the only protection is Better Auth's 3-per-10-seconds throttle (the docs say the two-factor lockout columns never engage, OA-S2-13), no per-account lockout was found. The panel buttons that change an account (Turn on, Turn off, Verify) were not pressed.
  • Not seen live: the second-factor challenge, the enrolment screen, the enabled state, the rate-limit message, a real session expiry, Turkish Security, the language dropdown itself. These are inferred from code and are marked so.
  • The Front Desk session in my isolated context was left signed in, because the app has no sign-out and I did not call the auth endpoint directly.
