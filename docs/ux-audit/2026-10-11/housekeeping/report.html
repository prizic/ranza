UX audit: Housekeeping

Route /en/housekeeping (and /tr, /ar), hosted staging, 2026-10-11, Property “Demo Otel İstanbul”. Roles: Housekeeping (primary), Front Desk, Manager. Mode: audit only, nothing was changed. Claims are labelled verified (I saw it), inferred (read in code or docs) or unknown.

Data state found: 3 rooms (101, 102, 201), none with a floor or building, 0 dirty, 2 clean and waiting for inspection, 1 inspected with a guest in house. One arrival today (201, not ready). Inspection is Off for the Organization and On for this Property. So “empty” and “60 dirty rooms” are inferred from code, not seen. I could not trigger a departure-driven dirty room (that needs a check-out, which is forbidden), so the automatic turnover is judged from the docs and tests only.

1. Verdict

  1. On a phone, this persona cannot mark a room clean from the Housekeeping page without hunting for the control. At 375 px the “…” menu that holds the mark actions is 336 px off-screen to the right of a horizontally scrolling table, and when you scroll to it the room number has scrolled out of view (HK-01, verified).
  2. The feature was designed for somebody else. use-case.mmd says “Housekeepers are not expected to use the app: whoever hears ‘204 is done’ records it”, and assigning work to a named housekeeper is out of scope (HK-DEF-04). An attendant doing 30 to 60 marks a shift on a phone is a different product than the one built. I think that premise is worth challenging if attendants are real users; if the desk really does the typing, the phone findings matter less and HK-04, HK-06 and HK-07 matter more.
  3. The good phone path exists but is on a different page: the Today page for the Housekeeping role has a “Clean these first” list with a priority badge and a one-tap “Mark inspected” button (verified, shot 10). It shows only the top 6 rooms and the Housekeeping page itself has none of it.
  4. Correctness and permissions are solid: the board reads the same in English, Turkish and Arabic (RTL mirrors properly), roles that may not mark see a read-only board, and a bad Property link lands on a calm empty state.
  5. Biggest risk: on a busy day (many dirty rooms) the board is a plain 10-per-page table sorted by building and floor, with no due-out or priority marker, no floor filter and 32 px tap targets (HK-02, HK-04, HK-05). That is inferred for volume, verified for the parts.

4. Top changes

  1. I can mark a room clean with one thumb, seeing which room it is — a card list with a full-width mark button below the tablet breakpoint (HK-01, HK-02). Highest frequency, biggest time saved.
  2. I can see which rooms to do first without opening another page — priority and “leaving / arriving today” on each board row, dirty-first default order (HK-04).
  3. The first screen is rooms, not totals — compact status chips that double as the filter (HK-03).
  4. I can finish a long list in one pass — sticky selection bar, “select all in this filter”, larger default page (HK-08, HK-09).
  5. I can pick my floor — a floor control and floor in search (HK-05).
  6. The front desk reads the same word for a room everywhere — one term and icon on Arrivals, Today and the board (HK-07), and an honest “Ready to let” (HK-06).
  7. I see that my tap worked, next to the room — inline confirmation or toast with undo (HK-08).
  8. Only controls I can use are shown — collapse the inspection card for non-managers (HK-11).

5. Inconsistencies with sibling screens

  • Today does this better. Today’s “Clean these first” carries priority badges and a single-tap mark; the Housekeeping page, the page the product calls the room board, does not (shots 09, 10). verified
  • Wording: “Waiting for inspection” (board) vs “awaiting inspection” (Today) vs “Not ready” (Arrivals, with the dirty icon). In Turkish the readiness tile is “Satışa hazır” (ready to sell) and in English “Ready to let”; fine, but both ignore occupancy (HK-06). verified
  • Mobile pattern: Today and the top bar are built for narrow screens, with a bottom navigation bar; the data tables are the part that is not (HK-01, HK-10). verified
  • Back button (ADR 0035): present on the Housekeeping page, leading edge, goes to Today and keeps the Property, mirrored in Arabic. verified (shots 01, 06).

6. Not built / needs backend work

  • Assignment to attendants / who cleaned it: out of scope, HK-DEF-04 in docs/features/housekeeping/edge-cases.csv. The audit log names who pressed the button; no work queue per housekeeper exists.
  • Do not disturb: not in code, docs, roadmap or blueprint (a case-insensitive search for “do not disturb” and “DND” found nothing). It is not even a deferred row, so if it is wanted it is a design decision, not a UX fix.
  • Out of order: owned by Maintenance (HK-DEF-06); the board just shows “Out of service” in Occupancy. Not seen live: no room is out of service on staging.
  • Daily cleaning of rooms still in use (stayover): deferred, HK-DEF-01, listed as “missing” in docs/roadmap.md. 102 (guest in house) is shown with a static status and has no “service today” state.
  • Per-bed status in a shared room: deferred, HK-DEF-02.
  • Auditing the worker’s automatic dirty mark: deferred, HK-DEF-03; the row’s null “changed by” is the only trace.
  • A phone-first attendant view: not in the roadmap or the screen handover (docs/handover/operator-workspace-screens.md lists housekeeping as built for the board). Treat as a new feature if attendants are to use it directly.
  • Departure-triggered turnover: built (HK-S1-01, HK-S1-22, worker); the board shows the room dirty even before the worker writes it. Not verified live in this audit.

7. What already works well and must not regress

  • Status is a word plus an icon, never colour alone, and “Clean · Waiting for inspection” separates two rooms the desk must treat differently (shots 02, 11). verified
  • Turkish and Arabic are complete on this screen, including plural rules, and the layout mirrors cleanly in RTL (shots 06, 07). verified
  • The Today “Clean these first” card: priority badge and one-tap mark (shot 10). verified
  • A room it is already in can be re-marked harmlessly, and a double submit is guarded by one shared in-flight state (HK-S2-06, code). inferred
  • Narrowing from Today (?show=, ?floor=) opens exactly the counted rooms and offers “Show all” (shot 09). verified
  • An unknown or unreachable Property shows an empty state, never another Property’s rooms (shot 13). verified
  • Permissions: the read-only banner copy, the capability gate and the refusal message are in place (code). Manager sees an editable Property setting and a disabled Organization one with the reason (“Only someone who reaches every Property can change the Organization’s setting.”). verified for text, setting not changed.
