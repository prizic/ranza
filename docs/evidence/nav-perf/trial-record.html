Trial record · Operator Workspace · PR #58 perf/soft-navigation

Page switching: before and after #58

Every number and image below was produced against two production builds running side by side on this machine, each against its own throwaway database. Nothing here is reasoned about; each claim names the capture behind it, and the raw data sits beside this file in data/.

PARTIAL

#58 does what it set out to do mechanically — 0 of 45 rail clicks load a new document (BEFORE: 45 of 45), the first visible change comes at a median 48 ms (BEFORE 204 ms), a page switch costs 1–3 tenant transactions instead of 12–14, and the chosen Property is kept — but it introduced a language regression (server-rendered copy turns Turkish after a rail click on /en and /ar), and on clicks that did not stall the page's data reaches the screen later than before (median 348 ms vs 134 ms).

Failures, first

  1. F1 — FAIL, regression from #58: wrong language after a rail click. On /en and /ar, every page reached through the rail renders its server copy in Turkish (e.g. Finance says “Folyolar — Deniz Otel Kadıköy” on /en); a reload of the same URL renders it correctly (“Folios at Deniz Otel Kadıköy”). The sign-in page reached by a soft redirect is Turkish too. BEFORE is correct in every case. Root cause: pages call getTranslations() with no locale and only app/[locale]/layout.tsx:61 calls setRequestLocale; a client navigation does not re-run that layout, so i18n/request.ts falls back to defaultLocale (tr). Same finding as the audit lane's F-2. Evidence ↓
  2. F2 — FAIL against the goal: data on screen is slower on an unloaded click. On clicks that did not stall (≤ 1.5 s): AFTER 25/45, BEFORE 26/45, AFTER's median is 348 ms (min 340) and BEFORE's is 134 ms (min 72). The skeleton from loading.tsx appears at ~48 ms and React then holds any Suspense fallback for at least 300 ms (globalMostRecentFallbackTime + 300 - now(), Next's bundled react-dom line 12097), so AFTER cannot show data before ~340 ms even when the server answers in ~15 ms. What AFTER wins is feedback, not data. Evidence ↓
  3. F3 — NOT IMPROVED here: stalls. 20/45 AFTER clicks and 19/45 BEFORE clicks took longer than 1.5 s (up to 14.7 s and 14.7 s). Postgres itself logged trivial statements taking 4–16 s in both builds; the Docker VM they run in has 4 vCPUs at load 50–129 with CPU pressure ~85–90 % from unrelated containers. #58 cut the statements the database had to run by 7.7× (665 vs 5103 tenant statements for the same 45 clicks) and the >1 s statements from 77 to 27, but in this environment that did not make stalls rarer. What changes is what a stalled click looks like: AFTER shows a skeleton within ~50 ms, BEFORE shows nothing until the new document arrives. Evidence ↓
  4. Pre-existing gap (not #58): when the database goes away mid-session, a rail click in both builds replaces the whole workspace — rail included — with Next's generic “This page couldn’t load”; there is no workspace error boundary. Evidence ↓
  5. UNVERIFIED: the mobile bottom dock, the Front Office group's children (arrivals, departures, reservations, rooms), an Organization missing some Entitlements, roles other than manager and front desk, and /tr (where F1 cannot show, since Turkish is the fallback). None was exercised. Details ↓

2 · Time to the first visible change, and to data on screen

How it was measured. Times start at the click event, taken inside the page. First visible change: for a soft navigation, two animation frames after the old content leaves main (the skeleton or the new page replacing it); for a full load, the new document's first-contentful-paint. Data on screen: two animation frames after main holds the new page with no aria-busy skeleton left in it (full load: the later of that and first paint). A click slower than 1.5 s is reported as a stall and never dropped. The screencast filmstrips further down check these in-page marks against painted pixels.

FAIL Data on screen, un-stalled clicks: AFTER 348 ms, BEFORE 134 ms. AFTER never went below 340 ms, on any page — Analytics, which reads almost nothing, included. The floor is the same on every page, including one that reads almost nothing, so it does not track the server's work; AFTER's navigation response starts arriving at a median 16 ms (BEFORE's HTML document: 185 ms), though a first byte alone does not prove the page's data had arrived. What the floor does match is React: once a Suspense fallback is on screen it is kept for at least 300 ms. In the react-dom Next 16.3.5 bundles (next/dist/compiled/react-dom/cjs/react-dom-client.production.js): 

12097:          ((exitStatus = globalMostRecentFallbackTime + 300 - now()),
13270:      300 > now() - globalMostRecentFallbackTime)

~48 ms to the skeleton + 300 ms held = the ~345 ms seen on every un-stalled AFTER click. This is a consequence of adding (workspace)/loading.tsx, which is also what makes the instant skeleton and the prefetch possible — a trade, not an accident, but one #58 did not state.

Filmstrips — painted frames from Chrome's own screencast

Chrome's Page.startScreencast emits a timestamped frame whenever the page repaints. The harness keeps the last frame before the click and every frame after it whose size changed by more than 2 % (a visible change, not the skeleton's pulse); every frame's offset and size is listed in data/cases-*.json. Stalled attempts were retried until one did not stall, and each attempt is recorded. The frames shown come from img/frames-*/; img/*-film-*.jpg are the harness's fixed-mark picks for the same clicks (last before, first after, +100 ms, +250 ms, first after the data mark), kept because the JSON names them, and img/frames-after-film-slow/ holds every saved frame of the slow click, the skeleton pulsing for eight seconds.
