# 0045. The first integration is a signed outbound webhook the worker sends, and refuses private addresses

## Context

The Integrations screen shipped in `20260916010000` with the vocabulary of an
integration — a card, a status, a failed-operations view, a Retry button — and
no integration. A review found that nothing in it ever called an external
system. Retry marked a failure `resolved` and flipped the card to `connected`
without sending anything and without counting an attempt; the copy promised
automatic retries that did not exist; the two definers a worker was meant to
call tested `current_user = 'ranza_worker'` inside `SECURITY DEFINER`, where
`current_user` is the owner, so their worker branch could not run; neither
checked reach or the commercial gate; an integration was matched by its display
name; `config` was plaintext JSON readable by everyone with `integrations.view`;
and the seed script fabricated four "connected" systems that nothing had
connected.

The ticket's "done when" is: one external system is connected and its failures
are visible without reading a log. Which system is a decision, and blueprint
section 13 forbids inventing an integration that no specification covers.

## Decision

### The system is an outbound webhook

An Organization registers an HTTPS address, chooses events, and Ranza posts each
of them to it as signed JSON. Blueprint section 13, Phase 5 lists "Public APIs,
webhooks", so it is specified. KBS, e-Arşiv/GİB, WhatsApp, payment providers and
a channel manager each need a contract and credentials nobody has given us, and
building any of them would mean inventing its half.

Six events can be subscribed to, all already in the outbox (ADR 0017):
`reservation.created`, `reservation.cancelled`, `reservation.no_show`,
`stay.checked_in`, `stay.checked_out` and `folio.line_posted`. The catalogue is
in the database (`app.webhook_event_keys`), where a check constraint and the
worker's handler both read it; the module and the screen restate it and a test
fails if the three disagree.

### An endpoint belongs to the Organization

It receives the events of every Property, so registering, removing and testing
one needs all four gates of blueprint 3.5 with reach to the **whole
Organization**: membership, `integrations.manage`, whole-Organization reach and
the commercial gate (`app.can_use_capability_in_organization`), the shape the
ledger migration gave reading the books. Reading needs `integrations.view` and
the commercial gate and not whole-Organization reach: where an Organization
sends its data is not hidden from a Manager of one Property. A delivery and a
failure belong to a Property, and are read, retried, cancelled and resolved with
that Property's reach.

No role holds a write grant on any of the three tables. Every write is a
`SECURITY DEFINER` function that asks the gates itself and answers one refusal
for all of them, because a definer bypasses the policies that would otherwise
ask.

### The secret is generated by Ranza, shown once, and held where only the worker's function reads it

The module generates 32 random bytes (`whsec_…`), the function stores it in
`webhook_endpoint_secrets`, a table that has no policy and no grant for
`ranza_app`, `ranza_auth` or `ranza_worker`, and the screen shows it once. The
worker receives it through `app.webhook_delivery_secret()`, for a delivery it
holds the lease on, in its own Organization.

It is **stored in plaintext in that table**. Signing needs the raw key, so it
cannot be hashed; the alternative is encrypting it under a key the worker
receives through its composition root, which is a new environment variable, a
rotation story and a second place the key must exist, in exchange for protecting
a database dump. That is a real gain and a real cost, and it is left as
INT-DEF-03 for the owner to weigh. Until then a leak of the database is a leak of
the means to forge Ranza's signature to the Organization's own receivers, which
is the worst case and no more.

### A delivery is a record keyed by (endpoint, outbox event)

A handler in the dispatcher's transaction queues one `webhook_deliveries` row per
subscribed endpoint with `on conflict do nothing` on that key, so the same event
is never queued twice for the same endpoint however many times the handler runs.
The body is frozen at that moment from the event's id and the keys the catalogue
lists, never from the payload as a whole: any member of an Organization can
publish an event with any payload for it (`events_publish_own_scope`), and
`folio.line_posted` publishes the line's `description`. Only listed keys whose
values are numbers, booleans, null or a short token without spaces leave. The
Property is found from the payload only if it is one of the Organization's own,
and from the Stay for `stay.checked_out`, which names no Property; an event
that names none raises, so the dispatcher records it rather than the event being
delivered unfiled or dropped.

A **test event** is a delivery with no outbox event and the type `webhook.test`,
filed at the Property the person is working in, one at a time per endpoint.

### Sending is the worker's, and outside any transaction

Queuing is a handler. Sending is a second job (`apps/worker/src/webhooks`) that
lists due deliveries across Organizations, claims each in its own Organization's
context for a five-minute lease, makes the request with no transaction open, and
records the outcome through one function. Holding a row lock while a slow
receiver thinks was the failure ADR 0017 already names.

Each request carries `Idempotency-Key` and `X-Ranza-Event-Id` (the outbox event
id, or the delivery id for a test), `X-Ranza-Delivery`, `X-Ranza-Attempt`,
`X-Ranza-Event`, `X-Ranza-Timestamp` and `X-Ranza-Signature: sha256=<hex>`. The
signature is HMAC-SHA256 over `<timestamp>.<body>` so that a captured request
cannot be replayed under a fresh timestamp. Delivery is at least once: a worker
that dies between the reply and recording it leaves a lease that expires, and the
delivery is sent again with the same key.

A 2xx delivers. 408, 429, any 5xx, a connection that does not complete and a
reply that takes longer than ten seconds are retried after 1 minute, 5 minutes,
30 minutes, 2 hours and 12 hours, after which the delivery is failed (six
attempts in all). Every other answer, redirects included, fails it at once. A
redirect is not followed, because the address it names has not been checked.

### The worker may not be turned on the network

An address is refused twice. Registration refuses it on its text: not `https`,
user information, a local name, or an address literal in a non-public range. The
connection refuses it on its address: the lookup the HTTP client connects through
returns the address that was checked, every address in the answer must be public,
and the connection is made to that address, so a name cannot answer twice.
Loopback, private, link-local (the cloud metadata address included), shared,
documentation, multicast, reserved, unique-local, NAT64 and 6to4 ranges are
blocked, and an IPv4-mapped address is judged as its IPv4 form.

The one exception is plain `http` to this machine, which a test needs to run a
receiver. It is a flag the worker's composition root reads, and **a worker with
`NODE_ENV=production` refuses to start with it set**. A database check allows
that shape of URL so the tests can store it; the module refuses it at
registration; neither is the guard.

### Failures are visible, and each way out says who and why

A failed attempt writes `failed_operations` in the same transaction as the
delivery: `retrying` with the next attempt's time while the schedule lasts,
`failed` when it is spent or permanent. `error` is a code from a fixed list the
screen says in the reader's language, beside the HTTP status and at most 200
characters of what the receiver said on one line. Never the worker's exception
text, and no body or header.

Retry puts the delivery back in the queue, due now. It resolves nothing: the
worker's next attempt counts, and only a delivery that arrives resolves the
failure. Cancel (only while retrying) and Resolve (only once failed) each need a
reason of at least three characters and record who and when on the failure and in
an audit record at the Property. Removing an endpoint cancels what was on its
way, by name, and keeps every row.

### What goes

`public.integrations` is dropped, with `failed_operations.integration_id` and
`.payload`, and the two old definers. The table held a per-Property card nothing
maintained and a plaintext `config`; an endpoint is the Organization's, so it is
not a row of a Property-scoped table. `failed_operations` keeps its rows. The
seed no longer fabricates systems.

## Consequences

The Integrations screen shows what is true: an endpoint is delivering, failing
or unused by what happened to its deliveries, and a failure carries what the
receiver answered. A failing receiver is on the screen within seconds of the
first attempt.

An Organization on a lapsed Subscription keeps delivering. The worker's writers
are not gated on the commercial gates, for the reason the ledger gives (a fact
that already happened must not be lost to a billing state, ADR 0040) but the
cost differs: this sends data out. Whether delivery should stop for a suspended
Organization is INT-DEF-04.

Editing an endpoint is not built; changing an address is removing it and adding
it again, which also rotates the secret. Rotation without that is INT-DEF-02. A
second integration will reuse the delivery record's shape (a failure with a
code, a schedule, a lease) and will not reuse its table, which is about
endpoints.

`tests/integration/webhook-delivery.test.ts` runs the real dispatcher, the real
handler and the real delivery pass against a receiver started in the test.
`tests/database/integrations.test.sql` asserts each gate denying on its own, that
the worker functions answer only the worker and that no application role reads
a secret. Each was watched go red by removing the clause it covers, with three
exceptions that are findings and not oversights: the membership conjunct of the
endpoint gate, and the membership and Property-reach conjuncts of the failure
gate, are implied by the clauses beside them (`has_organization_wide_reach`,
`has_organization_permission` and `can_use_capability` each need what they
restate), so removing one fails nothing. They stay, and the migration says why.

## Owner to confirm

1. An outbound webhook is the first integration, not KBS, e-Arşiv or a channel
   manager.
2. An endpoint is the Organization's, with whole-Organization reach to change it.
3. The signing secret is stored in plaintext in a table no application role can
   read (INT-DEF-03 is the alternative).
4. Six events, ids and facts only, no guest name, no description.
5. Six attempts over about fifteen hours, then stopped.
6. `public.integrations` and the seeded cards are gone.
7. Delivery is not gated on the Subscription (INT-DEF-04).
